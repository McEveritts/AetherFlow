# Self-Update Lifecycle

When triggered from the dashboard (`POST /api/v1/admin/system/update/run`) or via runner-mediated `af release deploy|rollback`, `aetherflow-runner.service` (`backend-rs/crates/af-runner/src/self_update.rs`) starts each update inside a unique per-launch transient systemd unit named `aetherflow-self-update-<command>-<channel>-<8hex>.service` via `systemd-run --collect`. A task running inside `aetherflow-runner` cannot survive restarting that runner, regardless of `KillMode=process`.

## Launch, Binary Resolution & Execution Mechanics

- **Default Native Engine (`NativeRustRelease`)**: `resolve_af_cli_binary()` (`backend-rs/crates/af-runner/src/lib.rs`) checks explicit `AETHERFLOW_CLI_BIN` first, then `env::current_exe().parent()` (`bin/af`, `af`) from the runner's immutable release slot before falling back to mutable `/opt/AetherFlow/current/bin/af`, `/opt/AetherFlow/current/af`, and `/usr/local/bin/af` (the same immutable-slot precedence applies to `package_script_roots()`, `resolve_release_manager_script()`, and `resolve_sandbox_script_path()`). The transient unit runs `af [--root <root>] release <command> --channel <channel> --local --config <job_conf> --job-status-file <status_json> --job-unit <unit>` so it executes in-process without dispatching back through `/run/aetherflow/runner.sock`. Setting `AETHERFLOW_FORCE_BASH_RELEASE=1` or `AETHERFLOW_RELEASE_ENGINE=bash` runs `deploy/release-manager.sh` in the same isolated transient unit.
- **Serialization & Mutual Exclusion**: Launch requests are validated, serialized against concurrent self-updates and in-flight Marketplace package lifecycle jobs (`PACKAGE_LIFECYCLE_MUTEX`, SQLite `package_lifecycle_jobs`, `LaunchOwner` lockfiles, and the shared maintenance lock), and acknowledged only after `systemd-run` accepts the unit. Active jobs reject duplicate requests.
- **Configuration & Environment Passing**: Non-secret preserved environment variables are passed to the transient unit via `systemd-run --setenv=KEY=VALUE`. A `0600` job configuration file (`<data_dir>/.self-update-jobs/<unit>.conf`) is persisted on disk and passed via `--config` for the worker to read (unlinked only if `systemd-run` launch fails). `af-runner` never writes GitHub tokens (`AF_GITHUB_TOKEN`, `GITHUB_TOKEN`, `GH_TOKEN`) or `AETHERFLOW_SKIP_PROVENANCE_VERIFY` into `systemd-run --setenv` arguments or `<unit>.conf`; instead, `af-release` and `deploy/release-manager.sh` read `HEALTH_ENDPOINT`, GitHub tokens (stored redacted in memory), and root-only `AETHERFLOW_SKIP_PROVENANCE_VERIFY` directly from `0600` `/etc/aetherflow/aetherflow.env` (unless `AETHERFLOW_SKIP_ENV_FILES=1`), with precedence `process env > explicit --config > aetherflow.env > default-fallback --config > compiled default`.
- **Durable Status & Receipts**: Because `systemd-run --collect` unloads completed transient units immediately, restart-surviving observability relies on private `0600` durable JSON receipt files written under `<data_dir>/.self-update-jobs/<unit>.json` (recording `af` CLI's `CliExitCode` mapping — `2` usage/config, `4` preflight/probe/lock, `7` rollback/execution failure — rather than raw `af_release::ExitCode`) and the release recovery journal (`${RELEASES_DIR}/.recovery_state.json`), queried via `POST /v1/self-update/status` on `af-runner` and exposed on `GET /api/v1/auth/system/update/status` (and `/api/v1/admin/system/update/status`).
- **Operation Identifiers**: An unqualified poll to `/api/v1/auth/system/update/status` (without `?job_unit=<unit>` or `?unit=<unit>`) reports `operationId` as the active non-completed receipt's `job_unit`, returning `state: "idle"` and `operationId: null` once all on-disk receipts have completed (or `null` when reporting `recovery_required`). Pass `?job_unit=<unit>` (or `?unit=<unit>`) to query a specific completed receipt's `job_unit`. Separately, `af-release`'s `.recovery_state.json` tracks its own internal `RecoveryState::operation_id` UUID. Status errors are never treated as successful updates.

## Running Binary Verification

`aetherflow-api` captures its version from its physical running executable on startup, not from the mutable `/opt/AetherFlow/current` symlink, and reports it on `/health/ready`. Before marking a deployment complete, `af-release` (`verify_running_release`) checks `/proc/<pid>/exe` for both `aetherflow-runner.service` and `aetherflow-api.service` against the candidate release directory so a healthy older process cannot satisfy the gate. The settings UI independently checks fresh runtime, selected-release, operation, and upstream-version data before reporting that the latest release is active.

## Standalone Recovery & Interrupted Deployments

- **Upgrading from Pre-Isolation Runners**: Older v3/early-v4 runners lacking transient systemd isolation must be upgraded once from a standalone root invocation (`sudo af release deploy --local --channel <stable|nightly>` or an independent root systemd service) rather than the old UI updater. On hosts with a custom `PORT`, `af release --local` reads `HEALTH_ENDPOINT` (and GitHub tokens) directly from `/etc/aetherflow/aetherflow.env` when not explicitly overridden in process env or `--config`.
- **Interrupted Post-Swap Deployments**: If a previous deployment stopped after switching `/opt/AetherFlow/current`, take an online SQLite backup (`sudo af backup create`) and preserve `${RELEASES_DIR}/.recovery_state.json`. Run `sudo af release rollback --local [--channel <stable|nightly>]` before starting a new deployment. The recovery guard intentionally blocks overwriting `.previous_release`; do not delete or edit `.recovery_state.json` to bypass it.

## Validation

Run the `backend-rs` and `frontend-rs` workspace tests, Clippy, WASM asset checks, and Playwright suites (see [Testing & Verification](./testing.md)).

The ignored Rust integration test `tests::updater_survives_caller_restart` in `af-runner` executes `python3 tests/self_update_systemd_smoke.py --test-binary <path>` against the Linux host's system `systemd` manager (`systemctl`, `systemd-run`, `runuser -u nobody`), driving `/v1/self-update` and `/v1/self-update/status` through `build_runner_router().oneshot(...)`. Release CI (`.github/workflows/release.yml`) compiles the test binary unprivileged in `working-directory: backend-rs` via `cargo test -p af-runner --lib --locked --no-run --message-format=json` and executes the extracted binary under `sudo` (`sudo "$test_binary" tests::updater_survives_caller_restart --ignored --exact --nocapture`) to verify that both native `af-release` and Bash updaters survive restarts of their calling service without touching production AetherFlow services.
